# 博士申请时如何展示这个项目

## 项目定位

把它介绍为「中英双语、结合业务入口与人工客服协作的 AI 服务交互原型」。最有说服力的部分是你如何发现并解决交互问题：模板式问答、历史丢失、问完无法继续办理、转人工需要重复说明、客户和客服权限混淆。现在这些需求能在一个实际运行的系统里展示。

它来源于六人课程小组，代码实现、调试及文档整理大量使用 AI 辅助。申请时据实说明你的需求定义、反馈和项目推进；不要说所有代码都是独立手写，也不要替组员编造贡献。

## 建议的五分钟演示

1. 打开自己的客户演示账户，展示聊天列表与六类业务入口。
2. 用中文询问「我想办张银行卡」，说明系统可以先理解用途再澄清。接着切换英文提问，展示按本轮语言作答。
3. 询问学生账户网上如何申请，展示对应业务按钮、填写、核对、确认和演示回执。强调准备窗口与提交请求是不同阶段。
4. 新建对话，再切回旧对话，展示历史没有丢失。
5. 在原对话请求转人工并点击按钮。在另一浏览器/电脑的客服账户接单、回复；回到客户页面查看同一上下文中的人工消息。
6. 展示 GitHub 的架构、测试和评测说明，解释结果支持什么、尚未验证什么。

只使用虚构测试信息，提前检查 API 和网络。官网托管可能受额度影响，本地离线版本可以展示流程；离线回答使用规则，不能当作在线模型效果演示。

## 你需要能解释的内容

| 可能被问到 | 应掌握的回答 |
| --- | --- |
| 你做了什么？ | 你定义并迭代交互目标，通过 AI 辅助工程实现和调试。列举你发现的具体问题与设计决定。 |
| AI 是自己训练的吗？ | 没有训练新模型；接入 DeepSeek API，实现上下文组织、知识检索、受限工具调用和界面动作。 |
| 为什么不是固定话术？ | 在线模式由模型理解当前目标与上下文，工具提供事实；离线模式确实包含规则，二者需区分。 |
| 如何检索？ | 中英文问题和别名的 TF-IDF；词特征权重 0.8、字符特征 0.2，按 FAQ 标识合并。没有向量数据库或训练检索模型。 |
| 能直接给用户转钱吗？ | 不能。模型只能返回允许的演示窗口，提交需要用户确认，所有业务数据为虚构。 |
| 为什么客服和客户不会混在一起？ | 账户能力、当前会话角色、记录归属、工单分配都在后端检查；隐藏按钮只是界面层的一部分。 |
| 如何联机？ | 不同浏览器连接同一个服务；SQLite 保留记录，可见页面每三秒拉取更新。不是 WebSocket。 |
| 92.3% 代表什么？ | 自编 78 个可评测问句中 72 个在前 3 条检索结果找到目标 FAQ，不代表回答正确率。80 题离线关键词代理指标为 71.25%。 |
| 在线效果有多可靠？ | 已记录 8 轮中英切换 API 检查全部通过，是小样本回归，不能泛化为总体质量或用户满意度。 |
| 研究价值如何证明？ | 当前有系统和设计过程，尚无正式用户研究；可以提出任务完成率、交接重复信息和双语一致性的对照实验。 |

## 后续最值得投入的工作

先充分理解代码中的一次请求路径，能自己解释从网页到模型、工具、数据库再回到界面的过程。然后制定独立评测题集和评分标准；条件允许时再进行有合适同意流程的用户任务实验。这样项目会从可展示的工程原型，逐步形成有证据支持的研究工作。
